# bobpick-manifests · 밥픽 쿠버네티스 매니페스트 (GitOps)

> 밥픽 3차 프로젝트(Amazon EKS 이관)에서 **클러스터에 무엇이 배포될지를 정의하는 저장소**입니다.
> Argo CD가 이 저장소의 `overlay/dev`를 지켜보다가, 커밋이 생기면 클러스터에 그대로 반영합니다.
> 매니페스트 설계·작성과 부하테스트는 박상준이 담당했습니다.

- 프로젝트 전체 소개, 앱 코드, 이미지 CI: [menu-recommend](https://github.com/sjparkjust-arch/menu-recommend)
- EKS 인프라(Terraform, 팀원 담당): [bobpick-infra · `3rd/eks-han`](https://github.com/sjparkjust-arch/bobpick-infra/tree/3rd/eks-han)

> 프로젝트 종료 후 EKS 클러스터는 삭제했습니다. 이 저장소에는 운영 기준값(파드 2~10개, 메모리 요청 128Mi)이 남아 있습니다.

<br>

## 배포 흐름

1. 앱 저장소에 push하면 GitHub Actions가 장기 액세스 키 없이 OIDC로 임시 자격 증명을 받아 이미지를 ECR에 올립니다.
2. 같은 워크플로가 이 저장소의 이미지 태그 한 줄을 바꿔 커밋합니다 (`ci: update image tag to ...`).
3. Argo CD가 변경을 감지해 자동으로 동기화합니다. Git에서 지운 리소스는 클러스터에서도 지우고(prune), 클러스터를 직접 바꾸면 Git 상태로 되돌립니다(selfHeal).
4. 롤백은 이 저장소의 커밋을 되돌리는 방식으로 설계했고, 9/23에 직접 시험했습니다 (아래 트러블슈팅 4).

<br>

## 구성

```
bobpick-manifests/
├── base/
│   ├── kustomization.yaml   # 리소스 목록 + 이미지 태그 (CI는 이 파일의 태그만 갱신)
│   ├── deployment.yaml      # 앱 파드: 롤링 업데이트, 헬스체크, 자원 할당
│   ├── service.yaml         # ClusterIP 80 → 컨테이너 8000
│   ├── ingress.yaml         # AWS Load Balancer Controller가 ALB 생성 (HTTPS, 파드 IP로 직접 전달)
│   ├── hpa.yaml             # CPU 60% 기준 파드 2~10개, 확장·축소 속도 정책
│   ├── migrate-job.yaml     # DB 마이그레이션 + 정적 파일 S3 업로드를 한 번만 실행
│   └── configmap.yaml       # 비밀이 아닌 설정 값만 (DB 포트, 리전 등)
└── overlay/
    ├── dev/                 # Argo CD가 추적하는 경로
    └── prod/                # 운영 환경 분리용 자리 (현재는 base와 동일)
```

이미지 이름은 `bobpick-app-image`라는 이름표로만 두고 실제 ECR 주소는 `kustomization.yaml` 한 곳에서 정하기 때문에, 계정이 바뀌어도 이미지 주소는 이 파일만 고치면 됩니다. (인증서 값은 `ingress.yaml`에서 따로 교체)

### 이 저장소 밖에서 연결되는 것

| 리소스 | 역할 | 관리 |
|---|---|---|
| Secret `bobpick-app-secret` | DB·Redis 접속 정보, SECRET_KEY 등 앱 설정 값 | Secrets Manager 값을 External Secrets Operator가 Secret으로 만듦 (팀원) |
| ServiceAccount `bobpick-app-sa` | IRSA로 앱 파드와 migrate Job에 S3 권한 부여 | IAM 역할은 인프라 브랜치에서 생성 (팀원) |
| Argo CD Application | `overlay/dev` 자동 동기화(prune, selfHeal), HPA가 바꾸는 `/spec/replicas`는 차이로 보지 않음 | 클러스터에 직접 적용 |

## 주요 설정과 이유

### 무중단 배포 · `deployment.yaml`

| 설정 | 값 | 이유 |
|---|---|---|
| 롤링 업데이트 | maxSurge 1, maxUnavailable 0 | 새 파드가 준비된 뒤에만 기존 파드를 내려, 배포 중에도 요청을 받는 파드 수 유지 |
| startupProbe | `/healthz/`, 최대 30초 대기 | 아직 기동 중인 파드를 실패로 보고 재시작하지 않게 |
| readinessProbe | `/healthz/`, 응답 대기 3초 | 헬스체크를 통과한 파드만 ALB에 등록 |
| livenessProbe | `/healthz/`, 응답 대기 3초, 실패 6회 | 부하 중 일시적인 지연으로 멀쩡한 파드가 재시작되지 않게 (아래 트러블슈팅 1) |
| preStop | 5초 대기 | ALB에서 빠질 시간을 준 뒤, 처리 중인 요청을 마치고 종료 |
| 자원 | 요청 CPU 250m · 메모리 128Mi, 상한 CPU 500m · 메모리 256Mi | 부하테스트 중 파드 메모리 실측 106~124MiB |

→ 롤링 업데이트가 진행되는 동안 **502 에러 0건**을 확인했습니다.

### 자동 확장 · `hpa.yaml`

- CPU 사용률 60%를 기준으로 파드를 **2개에서 최대 10개**까지 조절합니다.
- **늘릴 때는 빠르게**: 대기 없이 15초마다 최대 2배까지.
- **줄일 때는 천천히**: 5분간 지켜본 뒤 1분에 1개씩. 부하가 출렁일 때 파드가 생겼다 사라지기를 반복하지 않게 했습니다.
- 파드가 들어갈 노드 자리가 부족하면 Cluster Autoscaler(팀원 구성)가 노드를 8대에서 최대 12대까지 늘립니다.
- 처음에는 최소 4개로 정했지만 노드 메모리가 부족해 파드가 재시작되자, 배포나 장애 중에도 서비스가 유지되는 최소값인 2개로 다시 정했습니다.

### DB 마이그레이션 · `migrate-job.yaml`

- `initContainer`로 넣으면 파드가 늘어날 때마다 마이그레이션이 중복 실행되므로, **파드 수와 관계없이 한 번만 실행되는 Job**으로 분리했습니다.
- 기초 데이터(seed)도 Job에서 자동 실행하도록 추가했다가, 운영 중 수정·삭제한 데이터가 배포 때 원래대로 돌아갈 위험이 있어 되돌리고 수동 1회 입력을 유지했습니다 (`19b4b8e` → `12f2453`).

## 트러블슈팅

### 1. 150명 부하에서 503 에러 128건 → 0건

- **증상**: 14,854건 중 503 에러 128건(0.86%). 파드가 늘어나는 30초 구간에 몰려 있었습니다.
- **원인**: 헬스체크(`/healthz/`) 요청이 실제 사용자 요청과 같은 Gunicorn 워커(파드당 2개)를 나눠 쓰다가 기본 응답 대기 1초를 넘겼고, 정상 파드가 ALB에서 빠지면서 남은 파드에 부하가 몰렸습니다.
- **조치**: 응답 대기를 1초에서 3초로, liveness 실패 허용을 3회에서 6회로 조정했습니다 (`7bf212d`).
- **결과**: 같은 조건으로 다시 측정해 14,760건 중 에러 0건, 처리량은 그대로였습니다.

### 2. 400명 테스트 시작과 함께 파드 6 → 2개, 에러율 60%

- **증상**: 400명 테스트 첫 30초 구간의 에러율이 60.41%(503·504)까지 올라 테스트를 중단했습니다.
- **원인**: 한계를 더 보기 위해 HPA 상한을 6에서 10으로 올린 커밋(`79d7989`)을 Argo CD가 동기화하면서, Deployment에 적힌 `replicas: 2`까지 함께 적용해 파드가 6개에서 2개로 줄었습니다. Argo CD의 `ignoreDifferences`는 차이를 감지할 때만 replicas를 무시하고, 다른 이유로 동기화가 일어나면 Git 값을 그대로 적용하기 때문입니다.
- **확인**: 파드 수 기록과 커밋 시각을 대조해 원인을 찾았습니다. 파드가 2개로 줄어든 상황에서도 HPA가 78초 만에 2 → 4 → 7 → 10개로 늘렸고, 그 직후 30초 구간 에러율은 0.04%였습니다. 파드가 준비된 상태로 다시 잰 400명 테스트의 에러율은 0.05%입니다.
- **재발 방지**: Deployment에서 `replicas` 줄을 지우거나, 동기화 옵션에 `RespectIgnoreDifferences=true`를 넣으면 막을 수 있습니다 (아래 개선 과제).

### 3. 노드 자동 확장 검증 (팀원과 함께)

- 파드 상한을 20개, 메모리 요청을 256Mi로 임시로 올려 노드 자리가 부족한 상황을 일부러 만들고 400명 부하를 걸었습니다 (`153eb85`).
- Cluster Autoscaler가 노드를 8대에서 12대로 늘렸고(증설 결정 1분 20초, 노드 등록 2분 33초), 응답 시간이 3.1초에서 0.69초로, 처리량이 초당 109건에서 149건으로 회복됐습니다.
- 테스트용 임시 값은 프로젝트를 마친 뒤 운영 기준값으로 되돌렸습니다 (`67db6f6`, `b8cee3b`).

### 4. 커밋 되돌리기 롤백 시험

- 9/23에 매니페스트 커밋을 되돌리는 롤백을 시험했습니다 (`c3f8b8a` → `41e68d7`).
- 노드 자원이 부족한 상태에서 반영이 멈추는 문제를 겪었고, 매니페스트를 직접 적용한 뒤 Argo CD 컨트롤러를 재시작해 복구하는 절차를 확인했습니다.

<br>

## 개선 과제

- Deployment의 `replicas` 제거 또는 `RespectIgnoreDifferences=true` 적용 (트러블슈팅 2 재발 방지)
- liveness와 readiness 경로 분리 (liveness는 DB를 확인하지 않게)
- migrate Job을 Argo CD PreSync 훅으로 바꿔 배포할 때마다 자동 실행
- Argo CD Application과 ServiceAccount 매니페스트를 이 저장소에서 관리
- `overlay/prod`에 운영 환경 값 분리
